# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Barrens Voice reads World of Warcraft chat aloud (WoW Forever, Russian client), each player in their own voice: race voices cloned by F5-TTS from the Russian voice-over in the user's own game client (read from its CASC storage), or Russian Windows (SAPI) voices. Two parts: a Lua addon and a Python companion program for Windows. User docs (Russian): README.md; design, protocol, research notes: DEVELOPMENT.md.

## Commands

Tools come from mise: `.mise.toml` pins Python, uv and LuaJIT, points uv at mise's Python (`UV_PYTHON`) and lets mise create and activate `.venv` from the uv project (`python.uv_venv_auto`); every library (the tests' too) is a dependency of the uv project in `pyproject.toml`, locked in `uv.lock` - there is no `dev` group. `mise install` once, then:

- `mise run test` — every test: Python (numpy, pymorphy3, num2words installed, so nothing is skipped) and Lua
- `mise run test-py` / `mise run test-lua` — one side only; a single Python test: `mise exec -- uv run --locked python -m unittest discover -s companion/tests -k NumberAgreement`
- `mise run icon` — regenerate `addon/BarrensVoice/Icon.tga`, `Media/smile.tga`, the launcher's `companion/bv/launcher/icon.ico` (and `tools/icon_preview.png`) from `tools/make_icon.py`
- `mise run voices-table` — regenerate `companion/bv/game_voices.json` (FileDataIDs of each race voice's lines) from the community listfile (`tools/game_voices.py`, cached in `tools/.cache/`)
- `mise run build`, `mise run sign`, `mise run installer` — the release archive with `manifest.json`, its signature, the installer (Windows); CI runs exactly these. `mise run dictionary` — `dist/dictionary.json` + signature for the dictionary online
- `mise run hooks` — once per clone: `git config core.hooksPath .githooks`, whose `pre-push` refuses a release tag that is not ready (`tools/check_tag.py`: the files at the tagged commit through `release.release_problems`, the very checks CI's build refuses by; offline, well under a second, no tests); `mise run check-tag vX.Y.Z [<commit>]` checks one by hand. Branch pushes are not checked.
- The Lua tests `loadfile` the addon's files by relative path, so `test-lua` runs in `addon/BarrensVoice`; `test_protocol.py` runs the addon's `Protocol.lua` encoder with `luajit`.
- The companion runs only on Windows. Players install it with the installer (`uv sync --frozen` from `pyproject.toml`/`uv.lock`, the `cuda` or `directml` extra by the video card; docs/adr/0003); from the source, `companion/BarrensVoice.cmd` makes `.venv`, installs `requirements.txt` and swaps RUAccent's `onnxruntime` for `onnxruntime-gpu[cuda,cudnn]` when `nvidia-smi` exists, else `onnxruntime-directml` (DirectML stalls the game's frames for a whole denoising step; CUDA does not — `f5engine.PREFERRED`), then opens the launcher `BarrensVoice.pyw`; `BarrensVoice.cmd --console` runs `python -m bv` in the console; `--selftest` / `--selftest-f5` render test audio to files). Development happens on macOS; testing is on a Windows machine with the game, over SSH: copy `addon/BarrensVoice/*` (except `VoiceList.lua`, `CompanionStatus.lua`, `DictionaryOnline.lua` and `NewsData.lua`, which the companion writes) into the client's `Interface\AddOns\BarrensVoice\` and `companion/bv/*.py` into the program's folder; the addon picks changes up on `/reload`, the program on restart. Screen capture can only be tested in the user's desktop session, never from SSH. Never launch or kill the game while someone plays.

## Architecture

- **Transport — the pixel strip** (`addon/BarrensVoice/Protocol.lua` + `Strip.lua` → `companion/bv/capture.py` + `protocol.py`; the loop's side — window, grab, link, search — is `bridge.StripReader`, a frame's line goes through `__main__.Lines`). Addons can't write files and WoW only loads signed SAPI DLLs, so the addon paints each line as dark cells along the bottom edge of the screen (the default since 0.4.0; or the top, or a custom rectangle: `stripPlace`, `StripWindow.lua`; the companion learns it from `strip=` in the `control` frame or SavedVariables `stripGeometry`, and searches the whole window when it is not there, `locate.py`) and the companion grabs the WoW window (Windows Graphics Capture, `mss` fallback) and decodes it. Frame: sync cells, 4 calibration cells (the decoder takes its thresholds from them, so `P.LEVELS` can change in the addon alone), header with version/seq/length/CRC-16, UTF-8 payload. The strip frame has no parent: as a child of WorldFrame everything in UIParent (minimap, action bars) drew over it whatever its strata; parentless, its TOOLTIP strata puts it above UIParent and Alt+Z does not hide it. Back from the companion: Lua files in the addon folder, which the game re-reads at every load (login, `/reload`) but not during play — `VoiceList.lua`, `DictionaryOnline.lua`, `CompanionStatus.lua` (`companion/bv/status.py` writes the time every 15 s from its start; `Companion.lua` compares it with `time()` at load and says in the chat whether the reading works) and `NewsData.lua` (`companion/bv/news.py`, at start before the game is launched: the «Что нового» entries of `news.toml` its version shows, with that version - the program's, which `News.lua` compares and keys what was seen by); an addon install keeps all four (`model.GENERATED`). Each ships as an empty stand-in so the `.toc` has a file to load before the companion first runs (`/reload` does pick up changed and new addon files on Forever: docs/verified.md). Sound files as flags (`PlaySoundFile` empty vs valid, as wow-ai does) were tried and dropped: the WoW Forever client reports every file present at launch as playable. Chat lines carry `id=`; the companion skips ids it read (`SeenLines`).
- **Payload**: `kind␟sender␟race␟sex␟class␟channel␟options␟text[␟raw]` with `\x1f`; options `rate=;vol=;voice=;decl=;raw=1` come from `ns.LineOptions()` in `Core.lua`. Non-chat kinds (built by `ns.ServiceFrame` in `Text.lua`): `control` (settings, every 2 min), `dict` (the player's dictionary layer in parts), `diag` (a note for the program's log), `pause`/`resume` (CatQuest speaks / is silent: the player cuts the line and plays it again from its start on resume), `stop`, `reset`, `open` / `copy` (the companion opens a page of its own list `links.py` in the browser or puts its address on the clipboard - a click in the settings; an addon can do neither; the Battle.net community's «Открыть» needs no companion: the addon prints its invite link in the chat for the player to click, `LinkInChat` in `Core.lua`); a name before a line (with the place it was said in when that changed, `sayWhere`) ends with `\x04` (droppable when the same character goes on in the same kind and channel) or `\x05` (an emote's, kept), and rules apply to the line only, not the name; the companion speaks only kinds in `LABELS` (`__main__.py`).
- **Text pipeline** (order matters for context rules; the companion's part is `__main__.speech_text`, tested end to end by `test_logic.Pipeline` with the real default dictionary): addon cleans markup (a link becomes its name without brackets; a bracket pair inside a word is a masked "х") → companion unmasks disguised words (`unmask.py`: Latin look-alikes, digits inside words, asterisk swear words from its own list; asterisks around a whole word are emphasis and `@` before a name a mention, both dropped) → applies dictionary words/phrases/stems (`Dictionary.apply_words`; a word joined to the next by an apostrophe is no entry), marking whole-word replacements `\x02…\x03` (not stems: they keep the case typed) → declines marked replacements after prepositions (`morph.py`, pymorphy3) → dictionary regexes (`dictionary.py`; their replacements are always marked, and declension off only strips the marks, so it never changes what later regexes match), then number forms `N [a|b|c]` and ordinals `<N>` → `text.plain` (quest level tags dropped, brackets to spaces, capitals of 4+ letters lowered) → «ё» where «е» cannot be meant (`yo.py`, eyo-kernel's safe dictionary `yo_safe.txt`; not the name) → numbers to words agreeing with the next word (`text.agree`), or an ordinal where only one fits (`text.ordinal`; `NUMBERED` nouns such as «уровень» settle the cases grammar leaves open) → stress (`text.Accentor`, RUAccent; the dictionary's `+` wins; after the numbers, so number words get stressed too) → engine. Regexes see text after the word replacements (e.g. "кд" is already "кулд+аун").
- **Dictionary layers** (`Dictionary.lua`): the default `D.DEFAULT` lives in the addon; SavedVariables keep only the player's diff `dictionaryEdits` (changed/added blocks by key, deleted keys, header). Key = normalised words (`*` for stems) or, for a regex, its pattern (text before the last `=`). Changing a default entry needs no migration; changing a default regex's pattern needs `D.RENAMED[old] = new` (or a list of new keys when an entry became several; long strings `[[…]]`, because the companion parses the table itself: `dictionary.addon_renamed`). The companion applies the dictionary: it reads the default straight from the addon's `Dictionary.lua` and re-reads it when the file changes (no /reload needed), and gets the player's layer over the strip (`dict`) or from SavedVariables (`dictionaryUser`) - both `D.SentLayer`: `D.UserLayer` (changed/added lines and `!<default line>` for deleted ones) without the lines over `D.MAX_LINE` (480 bytes, a strip part), which the chat names once, so a rule never works in one session and not the next. The dictionary online (`bv/online_dictionary.py`): CI publishes the default, signed, to the branch `dictionary`; the companion uses it while its `revision` is newer than the addon's `D.REVISION` (0 in the repository, stamped by `tools/release.py`) and writes it into the addon as `DictionaryOnline.lua` (kept by addon installs). A change to `dictionary.json`'s shape or to the dictionary's syntax (a new kind of entry or replacement an older companion would misread) bumps `online_dictionary.FORMAT`: older companions keep their last dictionary.
- **Engines** (`engines.py`): the addon's choice per line; F5 is loaded at start while the game launches (unless the addon's saved variables say Windows voices) and unloaded when the addon switches to Windows voices (`Engines.follow`: not for a Windows voice sample, whose line carries `sapi=`); a failed load is retried after `RETRY_AFTER` (10 min) or on a switch to Windows voices and back. `speech.py` (SAPI via pywin32, voice per player by rendezvous hashing, per-engine stress format). `f5engine.py`: voice bank from the game client (`gamevoices.py` + `casc.py`: per race and sex the character voice and 3 NPC voice types listed in `game_voices.json`, lines transcribed and the joined reference checked by Whisper (`whisper_onnx.OnnxChecker`; `refcheck.py` scores the likeness), pitch-shifted copies; rebuilt when the game build changes, before the game is launched — `prepare_voices`, and when bank.json is damaged or a reference wav is gone; an empty bank is an error, not a silent ready; the reference's pace is its speech without pauses, `Slot.speech`), voice per character with memory (`assign.py`, `assignments.json`), lines split into statement runs and single questions (`sentence_groups`), `intonation.py` (Praat PSOLA: yes/no rise + last-syllable boost, peak on the wh-word), then `tidy`/`limit` loudness. One shared `audio.Player` plays everything in order; `stop` drops queued and in-flight lines by generation.
- **Launcher** (`companion/bv/launcher/`, tkinter, everything drawn on a canvas by `paint.py`): `model.py` holds the logic without a window (installed games by `Wow.exe` in each flavour folder, addon version from the TOC and copying it in, `config.json` edits, `describe` = the four state lines, the HKCU Run key; updates are `bv/update.py`'s `Updater`) and is what `test_launcher.py` tests; `process.py` runs the companion as a child without a console (`BV_LAUNCHER=1`, output read as its log), tied by a job object (kill on close, silent breakaway so Battle.net started by the companion survives), stopped through `tmp/stop`; exit codes 3 = start again online (`restart_online`), 4 = another companion runs (named mutex), 5 = `config.json` cannot be read (said in words, the file left alone). For a freshly applied version an end counts three ways (`App.start_failed` → `update.record_start`): an error at start is a failed start (two roll back), exit 0, an error after a run past `EARLY`, or the launcher's tick once the running companion is past `EARLY` (`App.settle_running`, once per run - a companion only ever stopped by the launcher would otherwise stay watched for good) settles it (`update.json` goes, older versions are pruned on a thread of their own), and 3, 4, 5 or an error the companion explained itself, whenever it comes (`state.json` phase `"error"`: no addon, say), are no verdict - neither failed nor good, `update.json` kept and nothing pruned, the next start decides. `state.json` is trusted without comparing pids: `Companion.start` deletes it before each start, and in a venv on Windows `python.exe` may be a shim whose pid is not the interpreter's. `install.prune` removes only folders named like a version (`VERSION_NAME`) older than the current one, reading update.json only after `app\current` (an update applied meanwhile keeps its `previous`), and keeping the newest of them that was not refused (update-refused.json keeps earlier refusals under `before`), update.json's `previous` and what `current.new`/`current.old` point at (a version newer than current - prepared, or refused - stays); a version is renamed to `<version>.pruned` before removal, so a prune cut short leaves no half version. It also runs 5 s after every launcher start without update.json (with «close with the game» the settle's prune is cut short by the exit). At start the launcher re-creates `app\current` from `current.new`/`current.old` after a switch cut short (`install.repair_current`), and `point_current` refuses a folder without `install.STARTS` (`.venv\Scripts\pythonw.exe` and `companion\BarrensVoice.pyw`, the files launcher.cs's `Starts` checks; a test holds the two equal). A rollback refuses the failed version before it switches; with no whole previous version it says once that going back is impossible (`stuck` in update.json). Changes config.json did not take stay pending in the window and go into every later write, and the companion is started with `--forever`/`--retail` and `--launch`/`--no-launch` from the window - config.json read again before each start with `pending` over it, so a hand edit made while the window was open counts. The companion reports its state in `tmp/state.json` (`bv/state.py`: phase, voices, device, linked, window, damaged) - the launcher never parses log lines. `--tray` = resident at Windows sign-in: waits for a game process, then starts the companion with `--no-launch`; Play starts it with `--launch`. The cross quits (tray only for auto-launch and `--tray`). Switches: `model.parse_args` / `USAGE` (`--console`, `--forever`/`--retail`, companion flags passed through, `--open settings|help|log`, `--scale`, `--pos X,Y`, `--updated` - the relaunch after an update, which never starts the game; released versions pass it, so it stays). DPI: `paint.ScaledCanvas` scales coordinates, widths and fonts from 100 % design pixels. The game folders: `dictionary.wow_roots` (`game_dirs` remembered from the running `Wow.exe`, `wow_dir`, every fixed drive) plus the registry and Battle.net's `DefaultInstallPath` in `model.find_games`. F5 ONNX models come from the HF repo `rgeraskin/barrens-voice-f5-onnx` (`f5engine.fetch_models`; card in `tools/hf/README.md`).
- **Logs**: every line `HH:MM:SS LEVEL message`; the level comes from the message via one table in `bv/logs.py` (modules log with a plain callable). `bv/share.py` wraps `onnxruntime.InferenceSession` (2 threads, no spinning) and lowers the process priority — the game first.
- **Config**: `DEFAULT_CONFIG` in `companion/bv/__main__.py`; new keys are written into the user's `config.json` on start, and `_help` is taken from `DEFAULT_CONFIG` at every start (the file's own is never kept; written back when it differs). `settle_numbers` makes values usable, each change logged: a number setting must be a finite number (text such as "8" is read as the number; NaN, Infinity, null take the default) and not under its `LEAST`; a dict or list setting of another type takes its default. The companion's own write of new keys or `_help` that fails (a read-only file) is logged and skipped, never exit 5. Read once at start (the launcher reads it again before each start of the companion). The addon's settings are `ns.DEFAULTS` in `Core.lua`.

## Conventions

- **Retail is supported as well as WoW: Forever.** Check every addon API, global, texture, atlas, chat event and `.toc` load condition in Blizzard's UI source of both clients (Gethe/wow-ui-source branches `forever` and `live`), and say what was checked on which. On retail, chat in instances and encounters comes as secret values (`ns.Secret`): new code must not touch them. Settings that only make sense on one client (CatQuest/Wayfarer waiting) say so or are hidden on the other.
- Commit messages: no Claude/AI attribution footer. Commits use the repo's git identity (Roman Geraskin; the e-mail stays out of the files). Commit only when asked.
- Default branch is `master`.
- Tools through mise only: exact versions in `.mise.toml`; Python libraries are dependencies of `pyproject.toml` (exact versions; `uv add <pkg>==<ver>` updates `uv.lock`, commit both, and add the same pin to `companion/requirements.txt` - `test_repo` keeps the two equal); tests and scripts run as mise tasks (`uv run --locked …`; add a task for a new script). No system Python, Homebrew LuaJIT, `pip install` or ad-hoc `uv run --with`. The companion's runtime on the player's machine is the installer's `uv sync --frozen` from the release's `pyproject.toml`/`uv.lock`; `BarrensVoice.cmd` + `companion/requirements.txt` serve a run from the source.
- Amending: a commit not pushed yet may be amended when that is the sensible thing (a fix-up of the same change, a forgotten file); a pushed commit is not rewritten — fix it with a new commit.
- Name: the display name is "Barrens Voice" (addon title, UI, docs); the addon folder and identifiers stay `BarrensVoice` (`BarrensVoiceDB` is tied to the folder name: renaming it would reset players' settings). In texts players read the parts have their own names, never mixed: «Barrens Voice» is the mod as a whole (its version, «Что нового в Barrens Voice», «аддон Barrens Voice»); the Windows program (window, tray, the reading) is «Barrens Voice Launcher» at first mention and in messages, «лаунчер» after that and in short labels («Мост к лаунчеру…»); the reading itself, the companion process, is «озвучка» («озвучка запускается», «озвучка остановилась»). «компаньон», «приложение-компаньон» and «программа» for it are code and developer words only (code, comments, DEVELOPMENT.md, CHANGELOG.md). The shortcuts, `Barrens Voice.exe`, the Windows «Apps» entry and the sign-in start keep the name «Barrens Voice»: renaming them would leave the old ones beside the new.
- Markdown: no hard line wraps. A paragraph or list item is one line; the renderer wraps long lines.
- Russian user-facing prose - everything a player reads: the addon's chat lines, tooltips and settings, the launcher, the program's log, the installer, `news.toml`, README and docs for players: written as a person writes, no semicolons (a full stop, a colon or a comma instead) and no telegraphic fragments. The addon's tooltips and labels name no chat commands (`/bv …`): `/bv help` lists them for whoever wants them, and only «Помощь» points to it («Список команд чата — /bv help»), as the game's settings panel says «или /bv в чате» beside «Открыть настройки»; a long tooltip goes in paragraphs (`\n\n`). A list item is short; its details go in a note under it (`  > …`, indented into the item), so a reader can skip them.
- The strip's protocol: bumping `protocol.VERSION` (and the addon's `P.VERSION`) keeps the previous version in `protocol.SUPPORTED` with its decoding, so a companion updated mid-game still reads the old addon until /reload (docs/update-strategy.md).
- Decisions that had real alternatives (a format, a dependency, how something ships or is versioned) get a short ADR in `docs/adr/` (Russian; Контекст, Решение, Альтернативы, Последствия; next number; added to the index in `docs/adr/README.md`). An accepted ADR is not rewritten: a changed decision is a new ADR that supersedes it. DEVELOPMENT.md says how things work, the ADR why.
- Before a push: read the unpushed commits (`git log origin/master..`). A commit that changes or fixes what an earlier unpushed one added is squashed into it (rebase with fixups, or rebuild the commits), so each pushed commit is one finished feature or fix, and the tests pass at every commit.
- CHANGELOG.md follows Keep a Changelog 1.1.0 with SemVer, as in its header:
  - Sections `## [X.Y.Z] - YYYY-MM-DD` (the GitHub release's publication date, UTC); the version in work is `## [X.Y.Z] - Unreleased` and gets its date at release (`tools/release.py` cuts the release notes by the `## [X.Y.Z]` heading). A link line per version at the bottom (`[X.Y.Z]: …/compare/<previous>...<this>`).
  - Inside a version: `### Added`, `### Changed`, `### Removed`, `### Fixed`, in that order, only those with entries.
  - An entry is a title line (`- Short statement of the change`, no full stop) and, after a blank line, a paragraph indented by two spaces: what a player sees and why. English; quoted UI and log text stays Russian.
  - `BREAKING:` opens the title of anything that no longer works as it did: a renamed or removed command, file, folder or setting, saved settings not carried over.
  - MAJOR is 0: MINOR for features and breaking changes, PATCH for fixes and docs only.
  - A version is described against the previous release: a change to something not released yet goes into that feature's entry (its final state), never a Fixed entry of its own; Fixed is only for what a released version did. Test builds (betas) are not releases: no sections or link lines of their own (a release with any is refused, `release.changelog_problem`).
- Updates: `companion/bv/update.py` and `install.py` run on every player's machine - changes to them, to the release archive or to the manifest need tests in `test_launcher.py` (UpdaterFlow, ReleaseBuild, OldClients). A release that changes these two files adds a frozen copy of them under `companion/tests/compat/<version>/` (and to OldClients): new releases must keep installing through the clients players already have. `OldClients.test_every_release_has_its_copy` enforces it for every release tag (betas 1-4 predate `compat`); update.py and install.py changed after beta 13, so the 0.4.0 tag needs `companion/tests/compat/v0_4_0/` and its OldClients test.
- The selfcheck contract (`companion/bv/selfcheck.py`, binding on every release): before a built version becomes current, the launcher installed before it runs `<version>\.venv\Scripts\python.exe -m bv.selfcheck` with the cwd `<version>\companion` (`update.version_runs`); exit 0 = the version starts, anything else refuses that version, the last stderr line being the reason shown; a check that could not run (timeout, OSError) refuses nothing. The module's name, place and this calling convention stay; what it imports is the release's own choice. A version without the module gets `update.FALLBACK_CHECK` (tkinter, `bv.launcher.app`, `bv.__main__`, `bv.update`, cryptography's ed25519). The released betas 1-13 run no such check at all: 0.4.0 is the first client that does.
- No local identifiers in the repo - files and commit messages alike: machine names (write "the test machine" / «тестовая машина»), local paths (`…\`, `<папка компаньона>`), WoW account and character names (made-up or lore names: `MYACCOUNT`, `Someone`, `Громмаш`), e-mails, user names. What is public stays public in the history: before a push run `git grep -i -f .git/info/local-identifiers` and `git log --format=%B origin/master.. | grep -i -f .git/info/local-identifiers` - that list of this machine's own words lives only in the local clone, never in a file of the repo (naming them here would publish them).
- The app's version lives in `pyproject.toml`, the addon's in `addon/BarrensVoice/BarrensVoice.toc` (`## Version`, raised only when the addon changed). A released addon version is immutable, test builds included: any change to `addon/` after a release raises `## Version` before the next one (the launcher replaces a game's addon only when its version is older; `test_launcher.AddonVersion` checks every tag). Test builds carry the addon's test builds (`0.4.0b1`, `0.4.0b2`…, raised only when the addon changes), a release its release version (`tools/release.py` refuses a release with a test-build addon). Every release has a «Что нового» entry in `news.toml` at the root, keyed by the program's version (`pyproject.toml`'s), so a release of the program alone has one too: written for players (Russian, «ты», short: what they will notice and what to do, no technical details, not the CHANGELOG retold), `kind = "big"` for a feature or anything that works differently (the window after login), `"small"` for fixes and dictionary words only (one chat line with its `summary`), newest on top, the `date` ("DD.MM.YYYY") set at release; no «→», en dash or «|». It is the GitHub release's description (`tools/release.py` `notes`: the entry, a link to CHANGELOG.md at the tag, the install line; a test build's: «Тестовая сборка выпуска X.Y.Z.», its own entry if it has one, then its release's entry) and reaches the game through the companion (`NewsData.lua`), so news never raise the addon's `## Version`. `release.release_problems` (CI's build, and the pre-push hook before the tag is public) refuses a tag that does not name `pyproject.toml`'s version, a broken `news.toml`, a test build without its release's entry and `## [X.Y.Z]` section (undated and «Unreleased» will do), and a release without a dated entry, a dated CHANGELOG section and its link line pointing at the tag, or with test-build leftovers (test builds' own entries - fold them into the release's - or CHANGELOG sections and link lines of test builds); `test_news` checks the file, every tag (a test build's through its release) and the version in work. A test build shows its release's entry and one of its own, made by the build (`tools/release.py` `build_entry`: the subjects of its commits since the last tag with a GitHub release, docs-only commits left out, in the archive's news.toml and the release's description, never in the repository's); a hand-written one (`0.4.1b3`) wins - on a test build its release's builds' entries come above the release's, newest first (`News.lua` `N.Visible`, `news.visible`) (DEVELOPMENT.md, «Что нового»). Roadmap (README «Roadmap»): stages, a version number is given at release - 0.3.0 released, 0.4.0 in progress (ONNX Runtime, the launcher, the installer with auto-update, the dictionary online, the in-game community in Battle.net); then the volume by the mouse wheel over the minimap icon, smileys read as words (xD «смеётся», T_T «плачет»…, «:)» and «<3» too) with a setting that keeps the pause, distribution (CurseForge/Wago), WoW Classic, race voices on the CPU with Piper (docs/piper.md), stress fixes sent by players. Russian only; a rewrite in Rust/C#/Go is unlikely (pymorphy3 has no mature equivalent).
- User-facing text (addon UI, README, program log) is Russian; code, comments and CLAUDE.md are English. The WoW client font has no "→" or en dash: use "=", "—" or "-" in addon strings.
- Reference clips, models and game audio are never committed: they are made or downloaded on the user's machine (F5 model CC BY-NC, game audio Blizzard's). The client is only read, never written, and the game process is never touched.
