# 0010. Звук через MME (переназначение звуковых устройств), не WASAPI

Статус: принято (26.11.2026, 0.6.0).

## Контекст

Программа выводит строку потоком через PortAudio (пакет sounddevice, `bv/audio.py`, `StreamOut`) на «Переназначение звуковых устройств» MME (Microsoft Sound Mapper). Форк [sokol-rc/barrens-voice](https://github.com/sokol-rc/barrens-voice) вывел звук через WASAPI и намерил, что первая строка после тишины начинается за 0,76 с вместо 8,6 с (его docs/tts-live-wow.md; почему — не выяснено). Чтобы сравнить, в 0.6.0 добавили `audio_wasapi` (только в config.json): общий режим WASAPI вместо MME и короткий беззвучный поток перед строкой после тишины (`wake`).

По учебнику правильнее WASAPI: это родной современный интерфейс звука Windows, Microsoft советует для новых программ его или то, что построено на нём. MME (waveOut) — старый интерфейс, с Vista он работает поверх того же микшера Windows и добавляет свой буфер. Но для нас важно другое: сколько ждать звука и куда он пойдёт.

## Решение

Звук — через MME, на «Переназначение звуковых устройств». WASAPI не используется.

Почему:
- **Задержка не решает.** У MME задержка вывода 213 мс, у WASAPI 25 мс: выигрыш не больше 0,19 с, когда синтез строки занимает больше секунды. По журналам обычной игры на установке игрока (24–26.11.2026, RTX 5070 Ti, 6 шагов, строки после 20+ с тишины) медиана «до звука» — 1,15 с на MME (25 строк) и 1,20 с на WASAPI (24): выигрыша не видно, сцены его перекрывают. Задержки форка в 8,6 с на MME у нас нет: самая долгая из тех 25 строк — 3,8 с (на установке игрока; спящая беспроводная гарнитура может дать больше — для неё у потока `FIRST_STALL`).
- **MME следует за выходом Windows по умолчанию, WASAPI — нет.** Проверка 26.11.2026 на тестовой машине кодом `StreamOut` беты 0.6.0b2: тон, выход по умолчанию переключался между строками и посреди строки (Realtek ↔ Steam Streaming Speakers), куда ушёл звук — по индикатору уровня каждого выхода. MME: следующая строка — на новом выходе, и строка, которая уже звучит, переходит на него сама. WASAPI: звук остаётся на старом выходе и между строками, и посреди строки; перечитывание списка устройств в `StreamOut` беты 2 (по смене `DRVM_MAPPER_PREFERRED_GET`) не помогло — сработало ли оно, не проверено. Microsoft пишет, что с Windows 7 высокоуровневые интерфейсы, Wave API среди них, сами переводят поток на новый выход по умолчанию ([stream routing](https://learn.microsoft.com/en-us/windows/win32/coreaudio/stream-routing-implementation-considerations)); с WASAPI это работа самой программы.
- **Один путь вывода.** MME остаётся в любом случае: через него звучит строка, которую WASAPI не принял. WASAPI — второй путь со своими обходами (перечитать список, разбудить вывод) и своими проверками.

## Альтернативы

- **WASAPI по умолчанию.** Быстрее на ~0,2 с по расчёту, на деле не видно; наушники, включённые во время игры, не слышат озвучку до перезапуска — пришлось бы следить за сменой выхода самим (`IMMNotificationClient`) и переоткрывать поток.
- **Оставить `audio_wasapi` как пробу.** Им пользуется только проверочная установка, а каждый, кто его включит, получит звук, который не идёт за наушниками.
- **Монопольный режим WASAPI.** Задержка ещё меньше, но звук игры и других программ на это время пропадает — не для озвучки чата.

## Последствия

- Строка начинается на ~0,2 с позже, чем могла бы с WASAPI; на слух на фоне синтеза этого не видно.
- Наушники и колонки переключаются в Windows как обычно — озвучка идёт за ними, ничего настраивать не нужно.
- `audio_wasapi` и `wake` предложено убрать (не решено; вернуть — из истории git). Если когда-нибудь понадобится задержка меньше (озвучка без синтеза, свои короткие звуки), это решение пересматривать новым ADR, вместе со слежением за сменой выхода.
